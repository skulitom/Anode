Windows-MCP in the background: keep using your mouse and keyboard while it clicks

Tested on 22 October 2026: we started Windows-MCP 0.8.8 inside Anode's hidden Windows session (the seat), and all 13 of its tool calls succeeded (7 from a script, 6 from Claude Code) with no USER_CONTROL pause, while the pointer on the PC's own desktop, sampled every 50 ms for 240 s, never moved and its foreground window never changed. Windows-MCP's control gate reacts to physical input in its own Windows session, and nobody types in the seat. Nobody used the PC during this run, so it shows that the agent stayed off the desktop, not yet how the gate behaves while someone works at the same time. Method, data and the setup steps are below.

We make Anode. Windows-MCP is CursorTouch's project (MIT); we don't maintain it, and this page isn't affiliated with it. Our numbers come from one run that you can repeat with the scripts listed under Method; everything about Windows-MCP's own behaviour links to its README, issues or source. If we got something wrong, open an issue and we will correct it.

Why Windows-MCP pauses when you touch your mouse

Windows-MCP 0.8.8 (10 October 2026) added a control gate. While the agent has control, moving your physical mouse far enough or pressing Ctrl+Alt+Shift+Backspace hands control back to you, and new tool calls are refused with USER_CONTROL until your mouse and keyboard have been idle for 10 seconds (README at v0.8.8, the ControlStatus tool). In 0.8.8 the gate holds back every tool except ControlStatus, including ones that never touch the screen (its gate tests), and it can't be turned off: as #475 reports, 0.8.8 has no --no-control option and silently ignores the [control] settings that the README on main documents. The reporter of #457 uses the same PC while the agent runs long jobs, and found the agent blocked most of the time after updating.

The short answer

  • To keep working while it clicks, on today's 0.8.8: start Windows-MCP inside Anode's seat, a second Windows session for your account with its own screen, pointer and keyboard focus. Your input doesn't reach the seat, so the gate has nothing to react to, and the agent's clicks and typing don't reach your desktop. The steps are below.
  • If you are on Windows Home: this doesn't work. Anode needs Windows 10/11 Pro, Enterprise or Education.
  • If you want to watch the agent work on your own desktop: plain Windows-MCP with the gate on. There, the gate is what lets you take over.
  • If you just want the gate off: Windows-MCP's main has an opt-out (--no-control, #458) and gate policies (#466), but no release has them yet; #475 asks for one. With the gate off, you and the agent share one pointer again. See when to use something else.
  • If you need a security boundary: neither. Use a virtual machine or Windows Sandbox, as Windows-MCP's SECURITY.md suggests. The seat runs as your user, with your files and network.

Set it up

These are the steps from Anode's guide, Keep working while Windows-MCP clicks, which is kept up to date. You need Anode installed and set up and uv. Windows-MCP 0.8.8 needs Python 3.14 or later.

1. Install Windows-MCP in a folder of its own

uv venv --python 3.14 C:\tools\windows-mcp
uv pip install --python C:\tools\windows-mcp\Scripts\python.exe windows-mcp==0.8.8
New-Item -ItemType File C:\tools\windows-mcp\config.toml   # an empty config of its own

If uv picks a free-threaded build (3.14t), pywin32 won't install. Name a regular build instead, for example --python cpython-3.14.7-windows-x86_64-none.

2. Save a start script

Save this as C:\tools\windows-mcp\start-windows-mcp.cmd. It listens on 127.0.0.1 only, turns off Windows-MCP's anonymous telemetry, enables only the six tools our run used, and writes a log next to it.

@echo off
set ANONYMIZED_TELEMETRY=false
"%~dp0Scripts\windows-mcp.exe" serve --config "%~dp0config.toml" --transport streamable-http --host 127.0.0.1 --port 8765 --tools ControlStatus,App,Type,Click,Screenshot,Snapshot >> "%~dp0server.log" 2>&1

--config points at the empty file from step 1, so a ~/.windows-mcp/config.toml left from an earlier setup (an auth key or TLS) can't break the plain http:// client config below. Our run's script had no --config and added --debug (as run); --config is documented in Windows-MCP's 0.8.8 README, not run by us. Any program on your PC can reach the port, and Windows-MCP's other tools include a PowerShell runner, so enable only the tools you need; its --auth-key adds a bearer-token check.

3. Start it in the seat

anode run starts a program inside the seat. Like every desktop command, it needs the desktop lease, which you release straight after. If you sign in to Windows with a PIN or Windows Hello, a new seat may stop at sign-in: choose Sign in… from the Anode tray icon (troubleshooting).

$env:ANODE_AGENT_ID = 'windows-mcp-start'
$lease = anode lease acquire | Out-String | ConvertFrom-Json
if ($LASTEXITCODE -ne 0) { throw 'Desktop acquisition failed.' }
$env:ANODE_LEASE_TOKEN = $lease.leaseToken
anode run C:\tools\windows-mcp\start-windows-mcp.cmd | Out-Host
anode lease release | Out-Host

Give it about 15 seconds to start listening (ours took 14), then check that the server runs in the seat's session, which anode status prints as seat session, not in yours:

Get-NetTCPConnection -LocalPort 8765 -State Listen |
  ForEach-Object { Get-Process -Id $_.OwningProcess } | Select-Object Id, ProcessName, SessionId

4. Point your MCP client at it

For Claude Code, add this to the project's .mcp.json (the config we used), or run claude mcp add --transport http windows-mcp http://127.0.0.1:8765/mcp. Other clients that speak streamable HTTP use the same URL.

{
  "mcpServers": {
    "windows-mcp": { "type": "http", "url": "http://127.0.0.1:8765/mcp" }
  }
}

5. Stop it when you're done

End the process that holds the port. This works across sessions:

Get-NetTCPConnection -LocalPort 8765 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess }

Don't run windows-mcp install for this: its sign-in task would also start Windows-MCP in your own session, where it competes for the port and your pointer.

What this does and doesn't show

  • Nobody used the PC during the run. The gate stayed quiet because its low-level hooks and raw input see only their own session; we haven't yet repeated the run with someone working at the same time. The sampler already separates the user's own pointer moves from any others, so that run can use the same scripts.
  • The seat removes your input as a trigger, not every trigger. In 0.8.8 the gate can also report USER_CONTROL, or stay at CONTROL_UNAVAILABLE, when its on-screen indicator stalls for more than a second, with nobody touching anything (#465, open; #478 is a related open report). That happens inside Windows-MCP, so it can happen in the seat too; restart the server if it sticks. Our run didn't hit it.
  • Taking control yourself: if you press Take control in Anode's viewer, your input does reach the seat, and the gate should then pause the agent as it would on your own desktop. Not tested.
  • Where your pointer was: away from Anode's hidden viewer. If it rests over the viewer's rectangle, Anode's pointer guard stops seat programs from moving it (architecture); in this run the guard had nothing to block.
  • The seat is a desktop of your own account, not an empty sandbox. Programs that start when you sign in also open there; two of ours did, and we minimized them for the run and restored them after. Windows-MCP's Screenshot and Snapshot see the whole seat, so close or minimize what you don't want captured.
  • Snapshot took 16–26 s, including retries on a window that was closing. We didn't time it outside the seat.
  • Claude Code's clear: true didn't empty the test window: its line went into the middle of the script's (the window's text). The test window is a plain WinForms text box that ignores Ctrl+A, so this is about the test window, not the gate. We used it instead of Notepad because Windows 11 Notepad keeps its tabs per user, so a Notepad in the seat can open the tabs you left unsaved in your own session.
  • Windows-MCP doesn't take Anode's lease. If other agents use Anode's own tools at the same time, both act in the seat. Don't run both at once.

When to use something else

Windows-MCP on your own desktop, gate on

When you want to see every click as it happens, take over with your mouse, or you're on Windows Home, this is the simpler setup: one tool, no second session, and the gate exists for exactly this.

The next Windows-MCP release

Its main README, read at 0ffef41 on 22 October 2026, documents three gate policies. The default, relaxed, gates only direct input (Click, Type, Scroll, Move, Shortcut, MultiSelect, MultiEdit, and App switch and resize), so Snapshot, Screenshot, FileSystem, Registry and PowerShell can run while you use the computer. --no-control turns the gate off, and the README warns that the agent's desktop actions can then interfere with your own input. None of this is released yet, and we haven't run it. Choose it once released if your agent mostly runs commands, files and screenshots, as in #457: then the relaxed policy may be all you need. Clicks and typing still wait until you've been idle.

Windows-MCP 0.8.7

The reporter of #457 pinned windows-mcp==0.8.7 (30 September 2026), the release before the gate. The agent then works whenever you do, on the same pointer and keyboard focus as you, and you stay on the older release.

A virtual machine or Windows Sandbox

When the agent's work must not reach your files, accounts or network, run Windows-MCP in a virtual machine or Windows Sandbox, as its SECURITY.md suggests. Anode's seat is desktop isolation only: it runs as you (what the seat is not isolated from).

Anode's own MCP server, without Windows-MCP

Anode's server does the same jobs in the seat (windows, accessible controls, screenshots, clicks and typing) with the lease built in, so you run one tool instead of two. Choose Windows-MCP in the seat when you already use its tools, prompts or clients, or want its PowerShell, Registry and FileSystem tools. Both are compared in Windows desktop automation for AI agents.

WindowsPC-MCP

ShikeChen01/WindowsPC-MCP came up in these searches. It is a different MCP server, not a way to run Windows-MCP: its README says it gives the agent its own virtual display through the Parsec Virtual Display Driver (installed on first run, with one administrator prompt), keeps the agent's clicks and typing to that display, and lists Windows 10 or 11 and Python 3.12 or later. MIT, 1 GitHub star, last commit 27 May 2026. From its README, not run by us.

Anode's limits

  • Windows 10/11 Pro, Enterprise or Education, or Windows Server, on x64. Not Home.
  • anode setup needs one administrator prompt; it turns on Remote Desktop and child sessions (what it changes).
  • With a PIN or Windows Hello sign-in, each new seat needs your Sign in… from the tray.
  • One seat per Windows session. Builds are unsigned, so SmartScreen may warn. Anode is young: 3 GitHub stars.

  • The run, 22 October 2026, 09:13 to 09:22 London time: the seat was signed in, no other agent held it, no game ran in it, and the two startup apps open there were minimized for the run. The test window is testpad.ps1. Comments in the published scripts were edited to remove our internal names; the code is as run.
  • Not done: a run with someone using the PC, a run with --config, and any run of Windows-MCP's unreleased main or of WindowsPC-MCP.
