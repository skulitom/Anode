Background computer use on Windows without a VM: Codex, Orca and a separate Windows session

An agent can test a Windows app without a virtual machine and without taking your mouse, keyboard or screen if it gets a second Windows session: in our six runs on 15 November 2026 with Anode 0.11.4's MCP server, driven by Claude Code, the agent built, tested and fixed the app in 5 of 6 runs, and in 8,491 samples over 437 s on the PC's own desktop the app never had a window there and neither it nor Anode ever had the foreground. Codex's own computer use can't do that on Windows: by OpenAI's docs, read on 19 November 2026, it "can’t operate in the background while you keep using the same Windows session" and they suggest a Windows virtual machine. Orca's works on your own desktop and needs the target window in front for mouse and keyboard actions (its UI Automation element actions don't), and the design docs of Microsoft's new session containers (MXC) say synthetic input is blocked inside them. We have not yet run Codex or Orca with Anode.

We make Anode. Codex is OpenAI's, Orca is Stably AI's and MXC, Agent Workspace and Windows Sandbox are Microsoft's; we are not affiliated with any of them. Everything about them below comes from their own docs, posts and issues, read on 19 November 2026 and linked, and we ran none of those features. Our numbers come from the six recorded runs published with our Claude Code guide, where the data and the commands to repeat them are. If we got something wrong, open an issue and we will correct it.

Last checked: 19 November 2026 (runs: 15 November) · Anode 0.11.4 · Orca 1.4.264 · MXC 1.1.0 (docs of 18 November) · Windows 11 Pro 25H2 (build 26200) · Next check by 19 December 2026, or sooner when Codex, Orca, MXC or Agent Workspace changes how agents use a Windows desktop.

The short answer

  • To have it now, on Windows 10 or 11 Pro, Enterprise or Education (x64), or Windows Server with a Remote Desktop host: install Anode, run anode configure codex and ask Codex to test the app with Anode's seat tools (steps below). Anode's seat is, in its README's words, "a Windows child session running as your user", with its own screen, pointer and keyboard focus.
  • If you need a security boundary: keep the virtual machine, or use Windows Sandbox. Anode's seat runs as you, with your files, saved sign-ins and network.
  • On Windows Home: Anode doesn't run there, and neither does Windows Sandbox. A virtual machine or a second device (OpenAI's suggestion for Codex) remain, as do the tools below that work in your own session or on a hidden desktop in it.
  • If you use Orca: Orca's own computer use acts on windows on your desktop. Element clicks and values go through UI Automation without moving your pointer, but coordinate clicks, drags and keyboard input are refused unless you allow it to bring the window to the front (details).
  • If you are waiting for Windows to do it: Agent Workspace, a separate session for agents, is still a private preview for Windows Insiders, and Microsoft's Ignite posts of 17 November don't mention it. MXC is generally available, but its session-container backend calls a preview Windows API behind an internal feature flag, and its design docs describe a session whose windows can't be seen from yours and where synthetic input is denied (details).

Set it up with Codex

From Anode 0.11.4's README and connecting Codex; we didn't run these steps with Codex for this page.

  1. Install and set up Anode with the install commands in its README (its installer checks the release archive's SHA-256), then run anode setup once and approve its administrator prompt. It turns on Remote Desktop and child sessions, and can restart Remote Desktop Services.
  2. Register it with the Codex CLI: anode configure codex | Out-Host. By hand, it is 
    codex mcp add anode -- "$env:LOCALAPPDATA\Programs\Anode\anode.exe" mcp
    plus tool_timeout_sec = 420 in the [mcp_servers.anode] table of ~/.codex/config.toml: Codex's default tool timeout is 60 seconds, shorter than Anode's startup wait. anode start --hidden before the first request avoids that wait too. codex mcp remove anode removes the registration.
  3. Ask for the test, and name the seat, so Codex doesn't reach for its own computer use. The request our runs used is prompt.txt: build the app, start it "in Anode's background seat, not on my desktop", type the spec's example, fix what's wrong and check again.

Anode does not change Codex's built-in computer use; it adds its own tools (seat_lease, seat_run, seat_observe, seat_click, seat_type, seat_screenshot and others) that act only in the seat.

With Orca

Orca (129,549 stars on 19 November; 1.4.264 the same day) runs Claude Code, Codex and other agent CLIs it finds on the PC, with your existing logins unless you add separate accounts, and lists MCP servers under its settings' integrations (settings docs). We haven't checked whether an agent started from Orca loads the MCP servers you registered with that CLI.

Its own computer use on Windows, which its computer-use docs (15 November) label beta:

  • Its launch-app asks Windows to start an app in the background; some apps still come forward on their own.
  • Element clicks, set-value, scrolls and secondary actions (Invoke, Toggle, Select, Expand and others) go through UI Automation when the control supports them, "without moving the pointer or sending keys", and typing into a text box by its element index works too.
  • "Some apps still bring their own window forward when driven this way (WPF apps do for most of these)".
  • Coordinate clicks, right-clicks and drags are refused unless you pass --restore-window; then the target window comes forward and the pointer goes back where it was. Keyboard input without an element is refused the same way while the window isn't in front.

Two open issues show where it rubs: #34364 (27 October, about macOS and Orca 1.4.242) is titled "Prefer provider-native background computer use": it reports that Claude and Codex sessions picked Orca's own skill, whose foreground actions "interfere with the user's mouse and ongoing work" (the issue says it hasn't measured how often agents pick it; Orca's docs now say its macOS actions run in the background), and #43335 (17 November, Windows 11 Pro) reports Microsoft Defender's AMSI blocking Orca's Windows computer-use script as "HackTool:PowerShell/EmpireGetScreenshot.C" on 1.4.261.

What we measured

Six runs on 15 November 2026, on Windows 11 Pro 25H2 (build 26200) with Anode 0.11.4. Headless Claude Code 2.1.325 (Sonnet 5.5 in four runs, Haiku 5.5 in two) built a small Windows Forms app with a planted bug, started it in Anode's seat, typed the spec's example, found the wrong total, fixed the source, rebuilt and checked again.

  • The task: 5 of 6 runs finished the whole loop and left the app showing the right total (Total: 92.00). The other one (run 4, Haiku) was refused Anode's window-closing tool by our own permission list, didn't close the app another way, and its rebuild then failed on the running app's locked exe; the Sonnet runs with the same list closed the app with its Close button.
  • The PC's own desktop, sampled about every 50 ms by a watcher in that session: 8,491 samples over 437 s. The app and Anode had the foreground in 0 of them; the app had 0 windows there, and its process ran in the seat's session only. No pointer move happened without input in that session, though someone was using that desktop during three of the runs (182 bursts of input).
  • Repeat it: the app, the request, the watcher and each run's calls are in the guide's Method and results.json.

What this doesn't show

  • Codex or Orca driving Anode. Our runs used Claude Code. Anode's tools are the same MCP server for any client, but a different model may choose different tools; we haven't measured that.
  • Codex's own computer use inside Anode's seat, or in a VM. We didn't run either.
  • MXC or Agent Workspace. We read their docs; we couldn't run them (one is gated, the other a private preview).
  • Speed or cost against a VM. Not measured.
  • Other apps and PCs. One small app on one PC, Windows 11 Pro.

What Windows itself offers agents

MXC session containers

Microsoft's post of 7 October calls a session container a way to run an agent "in a separate, OS-isolated session", "under a distinct Windows account and session", for "Long-running agents and automation that need a desktop or stronger separation from the interactive user", on Windows 11 only (Windows Developer Blog). Its Ignite post of 17 November says MXC "has been generally available on Windows 11 since October" and that "OpenAI has turned MXC on by default in Codex" (Windows Experience Blog). Neither post says which of MXC's backends Codex uses, and we haven't read OpenAI's own guidance on enabling it, which Microsoft's 17 November developer post points Codex users to.

MXC is open source (microsoft/mxc, MIT, 1.1.0 of 15 November). Its default Windows backend is the process container; the session container is the isolation_session backend. Its design docs for that backend, written for MXC's developers (as of commit e6960f7, 18 November), say:

  • it calls the OS API Windows.AI.IsolationSession.Preview, which "is gated on an internal Windows feature flag" (oneshot.md);
  • its one-shot runner gives each run "a fresh per-execution Windows agent user account", and doesn't support GUI applications: "No display server inside the session; only stdout/stderr captured" (the same file);
  • the newer doc for its state-aware lifecycle puts it differently: inside a live session, "window creation, GDI, and the session's own clipboard all work; only input injection is blocked", and SendInput returns ERROR_ACCESS_DENIED (state-aware-rust.md), while the session's windows are "unreachable and invisible" from yours;
  • this backend rejects every filesystem and UI policy field, and requires the network to be left fully open (the same docs).

So, from the documents: a session container gives an agent's commands what Anode's seat doesn't, a fresh Windows account that can't reach your per-user data (though, by those docs, with no filesystem or UI policy and the network open). Anode's seat gives what a session container's docs say it doesn't: a desktop the agent can see in screenshots and drive with clicks and typing.

Agent Workspace

Microsoft's support page (last updated 5 December 2025, read today) says agent workspace "runs in a separate Windows session", that "Each agent operates using its own account", and that it is "available in a private preview for Windows Insiders in a release coming soon"; the page hasn't changed since. It also says agent connectors running in the workspace are "now available on preview builds 26100.7344+". It names Copilot Actions as the feature that uses it, and we found no doc on running your own Codex or Orca agent there (Experimental agentic features). Microsoft announced it at Ignite 2025 as an environment where "agents can interact with software, just like people" (Windows Developer Blog, 18 November 2025). Its three Ignite posts of 17 November 2026 on the Windows blogs don't mention it, and those blogs had no later post by 19 November.

When to use something else

A virtual machine or Windows Sandbox

When the agent's work must not reach your files, accounts or network. Windows Sandbox is a disposable VM that comes with Pro, Enterprise and Education, not Home; closing it deletes everything in it, software installed on your PC isn't inside it, networking is on by default and only one runs at a time (Microsoft). OpenAI's advice for Codex's own computer use is a Windows virtual machine; we haven't checked whether the ChatGPT app runs in Windows Sandbox.

Codex's computer use, while you watch

When you're happy to hand over the PC for the task, or the target is an app you already have open: OpenAI's docs say to keep the target app visible on the active desktop and to "use a secondary device, a VM, or stop the task before using that desktop yourself" (Computer Use). Locked, background use is for macOS.

Tools that act on windows in your own session

When the agent must work with windows you already have open. Orca (above) and Cua Driver send UI Automation calls or window messages to one app's window on your desktop; Cua's docs list foreground input as "Needed for games, canvas apps such as Blender, and focus-polling apps". Our comparison of background computer use on Windows covers them, agent-desktop and GitHub Copilot's app in more detail.

A hidden desktop in your own session

Windows can also give a program a second, hidden desktop inside your session (CreateDesktop). offstage-windows (npm 0.1.2, MIT) runs Electron and Playwright test sessions there; its README says real OS input (SendInput) and the cursor don't reach the app, while Playwright's and CDP's input do, and that some endpoint-protection products may flag it. Use it when your tests already drive the app through Playwright or CDP. agentfenster, a commercial, closed-source app, says its MCP server works "on a second Win32 desktop inside your session" and "never takes your foreground, mouse or keyboard" (its README, 8 August).

Headless tests

When the check needs no desktop at all: an API call, a shell command or a headless browser test is simpler, as Anode's own README says.

Where Anode doesn't help

  • Windows Home, macOS and Linux; ARM64 is not validated.
  • Not a sandbox: the seat signs in as you, with your files, saved sign-ins and network, and your startup programs run there too.
  • Your open windows: the agent works only on windows in the seat. Apps that refuse to run twice won't run in both sessions at once.
  • One seat, shared by agents in turn; it runs unelevated.

The full list, with sources, is in the guide's Where Anode doesn't help and Anode's USAGE.md (startup programs in the seat) and SECURITY.md ("The seat runs unelevated").
